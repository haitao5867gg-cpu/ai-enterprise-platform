# 连接器长任务和运行进度

落在哪一层：**连接器（MCP）约定 + 运行时**。要跑几分钟的工具（渲染视频、Databricks 长作业、批量导入）不受工具调用 30 秒超时的限制：工具先交回一个任务，平台反复查它的进度，直到做完。进度显示在运行上，也经 `/v1` 给外部页面看。任何连接器照这份约定写，调用工具节点和智能体就能用，节点设置不用改。

参考 MCP 规范 2025-11-25 的 Tasks（`tools/call` 带 `task`，再 `tasks/get`、`tasks/result`）。平台用的 MCP SDK 还不支持 Tasks，所以先用普通工具实现同样的三步：交任务、查进度、取结果。以后 SDK 支持了，换成标准 Tasks，节点和运行这边不变。

## 连接器这边

### 交回任务

长任务工具被调用后，在工具超时以内（默认 30 秒）就返回，不等做完。结果（`structuredContent`，或者文字内容是这段 JSON）只有一个键 `aep_job`：

```jsonc
{"aep_job": {
  "job_id": "j_7f3a…",          // 1–200 个字符，这个连接器里唯一
  "status": "queued" | "running" | "done" | "error" | "cancelled",
  "progress": 0.42 | null,       // 0–1，算不出就 null
  "message": "渲染第 3 段，共 12 段" | null,   // 一句话，超过 200 个字符平台截掉
  "result": … | null,            // done 时的结果，和普通工具的结果一样
  "error": "……" | null           // error 时的原因，超过 2000 个字符平台截掉
}}
```

很快就做完的调用可以直接返回 `done` 和 `result`；也可以干脆像普通工具一样直接返回结果，不包成任务。

### 两个固定工具

同一个连接器另外提供：

- `aep_job_status`，参数 `{"job_id": "…"}`：返回同样的 `aep_job`。不认识这个任务（比如连接器重启后丢了）时返回工具错误。
- `aep_job_cancel`，参数 `{"job_id": "…"}`：尽快停下任务，返回 `aep_job`。可以不提供，平台取消运行时就不通知连接器。

这两个工具只给平台用：平台列连接器的工具时不列它们（数据源的工具列表、智能体能用的工具、调用工具节点能选的工具都没有）。

### 任务键

平台每次调用工具都在请求的 `_meta` 里带 `"aep/job_key"`（64 个十六进制字符）：同一次运行、同一个节点的同一次执行、同样的工具和参数，键就相同。

- 连接器收到的键对上一个还在排队、在跑或已经做完的任务时，返回那个任务，不开新的。平台重启后节点会重新执行，这样能接上原来的任务，不会把同一段视频渲染两遍。
- 对上的任务已经失败或取消时，用这个键开一个新任务：运行重试就是要重新做一遍。
- 任务和结果至少保留 24 小时。
- 不是长任务的工具忽略这个键。只有运行里的调用工具节点和智能体带键；数据工程节点、提交 PR 节点和单节点试跑不带。

排队、并发数、任务存在哪里都由连接器自己定。

## 平台这边

经平台调用的连接器工具（调用工具节点、智能体、数据工程节点、提交 PR 节点、单节点试跑）返回的是 `aep_job` 时，按任务处理：

1. 已经 `done`：直接用 `result`。
2. `queued` 或 `running`：头 30 秒每 2 秒调一次 `aep_job_status`，之后每 5 秒一次。每次查询按普通工具的超时（同一个数据源的工具超时，默认 30 秒），但不超过长任务剩下的时间（见第 7 条）。
3. `error`：节点以 `tool_error` 失败，`error_message` 是「工具报错：」加上任务的 `error`。可以重试，重试会开新任务。
4. `cancelled`（连接器自己取消的）：以 `tool_error` 失败，「工具报错：任务被连接器取消了」。
5. 查询时连不上连接器（比如它在重启）：接着查，连续 2 分钟都连不上才以 `tool_error` 失败：「连不上数据源「…」：…」。
6. `aep_job_status` 报错（比如连接器不认识这个任务了）：以 `tool_error` 失败，「工具报错：查任务进度失败：…」。
7. 从交任务算起超过 `AEP_TOOL_JOB_SECONDS`（默认 7200 秒）还没做完（时限过后才回来的查询结果不算）：平台调一次 `aep_job_cancel`，节点以 `timeout` 失败：「长任务超过 7200 秒还没做完，已经取消」。
8. 运行被取消：平台调一次 `aep_job_cancel`（最多等 5 秒，失败也不管），运行停在这个节点。运行在别的进程里跑时，那个进程每次查完进度都看一眼运行是否取消了，不管这次查到了结果还是查进度出了错：取消了就不用查到的结果（哪怕任务已经做完），也不报查进度的错，同样调 `aep_job_cancel` 后停下。取消不算节点失败：节点的 `on_error` 不生效（不重试、不用默认值、不走失败分支），智能体也不再接着调模型和工具。
9. 平台进程停止（部署、重启）时不取消任务：运行还是 `running`，重启后节点重新执行，用同一个任务键接上原来的任务。
10. 不合格的 `aep_job`（不是对象、缺 `job_id`、`status` 不认识）：以 `tool_error` 失败，「工具返回的任务格式不对：…」。

节点的产出、智能体看到的工具结果，都是任务的 `result`，和普通工具一样。除了运行被取消，节点的 `on_error`（重试、默认值、失败分支）照常生效。

## 运行的进度

运行记录（`GET /runs`、`GET /runs/{id}`，`backend/src/aep/api/runs.py`）加一个字段：

```jsonc
"progress": {
  "node": "render",              // 报进度的节点，就是 step.node
  "percent": 42 | null,          // progress × 100 四舍五入，0–100
  "message": "渲染第 3 段，共 12 段" | null,
  "updated_at": "…"
} | null
```

- 只在运行 `running`、并且 `progress.node` 等于 `step.node` 时有值，其他时候是 null。每个节点开始时清掉上一份进度，所以不会显示已经走过的节点的旧进度。
- 现在只有长任务报进度：每次查到的 `progress`、`message` 有变化就写上。以后逐项处理节点也会报「第几项，共几项」。
- 运行页在「进行到「渲染」」后面接着显示「42%，渲染第 3 段，共 12 段」。

`/v1` 的 `RunResult`（[app-access.md](app-access.md)）加 `step`（同运行记录的 `step`：`{"node", "title"}` 或 null）和 `progress`（同上）。外部页面按 `step.node` 把节点归到自己的几段进度里（比如教练页面的「转写配音、排镜头、找素材、渲染」），再显示 `percent` 和 `message`。MCP 的 `get_run` 返回的就是 `RunResult`，也带这两个字段。

## 设置

| 变量 | 默认 | 说明 |
| --- | --- | --- |
| `AEP_TOOL_JOB_SECONDS` | 7200 | 一个长任务最长多久，超过就取消并以 `timeout` 失败 |

## 测试

后端测试用进程内的假长任务连接器（`tests/fake_connector.py`）：

- 交任务后查几轮才做完；一开始就是 `done`；直接返回普通结果的工具不受影响。
- 任务失败、连接器取消、`aep_job_status` 报错、格式不对，各自的 `error_type` 和说明。
- 查询时连接器暂时连不上，恢复后接着查完；一直连不上就失败。
- 超时后调 `aep_job_cancel`；运行取消时调 `aep_job_cancel`，节点不重试、智能体不再接着做；进程停止时不取消，恢复后接上同一个任务。
- 同一个节点重新执行时带同样的任务键；节点再次执行（循环）、参数不同时键不同。
- 进度写到运行上，下一个节点开始时清掉，运行结束后是 null；`/v1` 和 MCP `get_run` 返回 `step` 和 `progress`。
- 列工具时不列 `aep_job_status`、`aep_job_cancel`。
